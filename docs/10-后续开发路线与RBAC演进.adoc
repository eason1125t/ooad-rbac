= 后续开发路线与RBAC演进
:toc:

本文件仅定义后续方向和验收门槛，本轮不执行这些业务开发。用户已确认的v2规则不因模型演进自动失效；新增功能仍先契约、测试设计、新迁移，再实现。

== 正确区分模型与开发阶段

[cols="2,4,5",options="header"]
|===
|模型 |标准含义 |本项目状态
|RBAC0 |用户、角色、权限及分配关系的基础模型 |当前已实现核心及管理链，完整业务接入仍待补齐
|RBAC1 |RBAC0加角色继承层次 |仅规划；行政组织/管理员层次不是角色继承
|RBAC2 |RBAC0加约束，可讨论静态及动态职责分离等 |仅规划；不等于“只有静态约束”
|RBAC3 |角色继承与约束的组合 |仅规划；不等于“只增加动态约束”
|===

术语依据 https://csrc.nist.gov/csrc/media/projects/role-based-access-control/documents/sandhu96.pdf[Sandhu等的RBAC模型论文]及 https://csrc.nist.gov/Projects/role-based-access-control/faqs[NIST说明]。原计划“继承→静态约束→动态约束”仍可作工程顺序，但不能当作四模型的定义。

== P0：先完成稳定的完整RBAC0

[cols="2,5,5",options="header"]
|===
|切片 |主要交付 |进入下一阶段前的判据
|管理补齐 |应用/资源/权限点CRUD、实现状态、已有授权引用的组织移动影响预览；受限审计与必要体验 |未实现点不能新授；移动不绕范围；启停影响清晰、预览与版本一致
|导入 |组织、员工、建号、负责人、目录/角色模板分批预览/确认，受控反馈与幂等 |非法整批回滚、无姓名猜测/默认建号/岗位自动授权，重试不重复写
|OA |独立公文/审批历史表、本人草稿与单审批人最小闭环 |SQL数据范围、自审/状态/并发/审批人失权反例通过
|PMIS |独立项目/审批历史表、立项最小闭环 |预算/日期、本人/审批人、状态机及范围与OA分别验证
|工程验收 |回归、备份恢复、负载实测、课程材料 |真实报告与版本评审；需要缓存时另立可靠一致性切片
|===

=== 导入已定边界

仅.xlsx，20MiB以内、单表最多50,000行/100列、解压累计100MiB；不接宏/公式/外链。组织、员工、建号、负责人、权限模板是五种独立批次，各自校验→预览→确认→单事务，不把整工作簿说成一个跨批次事务。

不以姓名/电话识别员工，不从岗位推断角色。负责人同名留待绑定；未知动作或缺“全部”动作白名单阻断对应批次。默认仅新增，更新需显式差异与expectedVersion；不因文件缺人自动停用存量。

预览24小时，提交重核指纹/映射/依赖版本；幂等键包含文件hash、映射版本、类型和请求键。文件完成7天后禁止下载并标待人工清理，反馈90天后停止在线提供；原始Excel不进日志/Git，遵守禁止批量删除。具体原始映射保留在12与历史附件记录。

=== OA最小闭环

公文包含稳定编号、标题1–160字、纯文本正文最多10,000字、创建人/创建组织、指定审批人、状态、版本和时间。DRAFT或REJECTED本人可编辑/提交；SUBMITTED可本人撤回、指定他人通过/驳回；APPROVED、VOIDED终态。驳回意见1–500字，不允许自审，审批与撤回并发仅一个成功。

创建人来自认证主体；草稿/驳回可本人作废。审批人失权/离职不能继续审批，发起人可撤回重选，不自动改派或超级管理员代批。第一版无富文本、附件、会签、抄送或多级审批；角色模板只供配置，不因岗位自动赋予。

=== PMIS最小闭环

项目含稳定编号、名称1–160字、说明最多2,000字、计划起止日期、非负DECIMAL(16,2)预算、创建人/创建组织、审批人、状态和版本。创建者为负责人，不代建/转交。DRAFT、SUBMITTED、APPROVED、REJECTED、CANCELLED按本人/指定审批人及权限范围流转；结束日期不能早于开始，APPROVED与CANCELLED终态。

第一版不做合同、付款、进度、多人项目成员、附件或结项，不允许编辑已立项预算来绕变更流程。OA/PMIS各自模型与状态机，不使用万能业务表。

== P1：RBAC1角色继承

设计一个单应用内的角色有向无环图，明确“高级角色继承低级角色权限”的方向，区分直接权限与继承来源。组织上下级和管理员责任不直接转换成继承边。

新增边前用可达性检测环；事务中处理并发加边，防止分别无环、合并成环。角色停用、成员/权限有效期及范围沿继承路径如何生效须先写契约和测试，不能由图形界面自行推断。

新增/扩大继承造成的完整权限与范围必须纳入P∩D及受影响人员预览，禁止通过继承绕过通用角色、平台角色保护或自授限制。源角色改变会影响继承者，这是明确的策略变更，不能套用“授予者失权不级联”来忽略它。

建议新增独立继承关系迁移和公开解析接口，不把组织闭包表复用成角色图。验收至少覆盖链式/菱形继承去重、环/跨应用拒绝、来源说明、时间范围、停用及并发。

== P2：RBAC2约束，先静态后动态

=== 静态职责分离（SSD）和基数

例如“录入员、复核员不能同时分配给同一人”，属于分配时约束。先明确互斥集合及允许数量阈值，再定义角色人数上限、前置角色等确有业务依据的约束；不因为模型能支持就一次性增加所有类型。

所有入口共同校验，包括成员批量、人员完整集合、调岗、导入和继承策略改变；不能只在某个表单提示。使用稳定锁与唯一/约束策略处理并发分配，冲突整批回滚并审计。

=== 动态职责分离（DSD）

例如同一人可以被分配录入与复核角色，但同一会话不能同时激活冲突角色。当前RBAC0激活全部有效已分配角色，没有显式激活子集；DSD必须先设计会话角色选择、切换、存储及撤权失效机制。

业务请求只使用服务端校验后的活动角色，活动集合必须是当前仍获授权角色的子集。角色/继承/约束变化后旧活动集合要重新校验，不能信任客户端传来的角色列表。激活与切换需要CSRF、版本和审计/必要安全日志，多设备会话按已定语义隔离。

“不能审批自己创建的记录”是记录级业务职责分离，也需要服务端规则；仅DSD或角色互斥不能替代它。

== P3：RBAC3组合验证

在继承与SSD/DSD各自稳定后验证组合：继承得到的间接角色能否触发互斥、图变化如何影响分配和活动集合、冲突用户如何迁移，以及范围/有效期/双上限如何贯穿完整权限闭包。

升级已有数据前先扫描冲突并输出受限预览，定义平台修复流程；不能静默裁掉员工既有角色，不能因管理员本人失权生成追溯撤权。安全约束变更导致拒绝和主动修改共享角色一样属于明确策略变更，必须另有影响预览与审计。

最终验收是“继承+约束+所有既有RBAC0/v2回归”，不是只增加一张动态约束表。明确每阶段DDL、API、页面、迁移及反例，再授权开始实现。

== 性能与可靠性方向

用户确认目标为10,000在线会话、约1,000请求/秒，不等于10,000QPS。参考8vCPU/16GiB/SSD，独立压测机；预热2分钟、稳态15分钟，80%业务读/15%管理读/4%写/1%登录，记录真实硬件、数据和预期拒绝。

目标为授权热路径p95≤30ms、受保护读≤150ms、普通写≤500ms、登录≤1秒，非预期失败率<0.1%；10,000行导入预览≤60秒、提交≤120秒。规划样本至少10,000人、111组织、18应用目录、500角色、2,000动作，每人平均3角色，OA/PMIS各100,000记录。这些是目标与合成负载，不是实测达标或附件动作数。

先分析SQL/索引与范围读取；需要缓存时，另做事务outbox、分域版本、nextChangeAt、幂等消费、丢消息对账、故障拒绝及重连回归。不能用TTL或Redis订阅消息代替撤权一致性，不为了性能删除上限和范围检查。
