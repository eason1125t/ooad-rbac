== D01：管理职责、责任归属与权限上限

=== 管理层次与责任人员

采用平台管理员→应用业务管理员→普通业务用户三层职责；这是管理关系，不是RBAC1角色继承。
平台可以为同一应用任命多名业务管理员，同一人也可被分别委派多个应用；每份委派独立配置应用、人员组织范围、通用角色清单、权限点上限及有效期。第一版不允许业务管理员继续任命子管理员。
普通账号在每个应用至多指定一名当前责任管理员。人员组织必须位于该管理员的管理范围内；组织范围重叠时由平台明确指定，不按创建者、部门经理或最后操作者自动推断。不同应用可有不同责任管理员。责任关系只决定谁可以维护授权，不决定已经成立的授权是否生效；管理员离岗后可暂标待接管，平台可继续维护，普通用户既有权限不因此失效。平台负责责任指定、转交与管理员任免；业务管理员不能借组织范围重叠修改他人负责的人员。
业务管理员本人的业务角色、委派资格、人员范围及责任归属只能由平台管理，业务管理员不能给自己或另一名业务管理员改角色、权限或委派。业务管理员仍可以修改自己的密码，不能借此改动授权。
平台管理员不因平台身份自动拥有读取OA/PMIS业务记录或审批的能力，仍需显式业务角色；其平台管理能力是管理员委派的根，不是普通下属权限。

=== 有效权限与防止拼接提权

对应用a和操作时刻t，令P(m,a,t)为业务管理员m当前有效业务权限，D(m,a,t)为平台委派的可委派上限；本次新增/扩大授权上限C(m,a,t)=P(m,a,t)与D(m,a,t)的交集。委派、账号或应用无效时该管理员不能再执行授权写入。
普通用户的有效权限只由自己的有效账号、应用、角色、权限点、成员/角色权限关系、有效期及适用范围计算，多来源合并。运行时不与授予者或当前责任管理员的权限取交集，也不要求授予者继续在职、拥有权限或委派有效；责任管理员缺失不影响既有授权。granted_by仅记录历史来源及审计，不是权限生效依赖。
新分配角色时校验角色完整权限定义（含已配置未来权限）均在C内；修改既有角色权限/有效期/范围时，只检查新增或扩大部分是否在当前上限内，并预览全部成员影响。原有保留部分不因当前维护者权限较小而被静默裁剪。纯撤销操作检查管理资格、责任及范围，不要求操作者自己也拥有被撤销的业务动作。禁止拆分角色、修改共享角色或延长授权期限绕过对新增权限的校验；越界写入整次拒绝。
“下属权限不超过管理员”据用户最新要求改为操作时对新增/扩大授权的限制，不再作为全时刻不变量。历史合法权限与以后新授予权限的并集可能大于新管理员本人权限，这不触发追溯撤销。不同应用独立检查。
权限点与数据范围分别检查：相同动作也不能被授予更宽的业务数据范围。SELF是以目标账号为主体的范围模板，不把“员工能看其本人记录”误判成必须能看管理员的本人记录；ORG/ORG_SUBTREE的节点集合、ALL等范围上限另行包含校验。
授予业务权限不等于授予平台管理资格。平台管理权限点不允许进入普通业务角色；不使用角色名称或客户端传入的操作者ID判断管理资格。

=== 通用角色与专用角色

应用通用角色由平台维护，新授予时其清单和完整权限定义须符合管理员当前上限。组织专用角色绑定责任业务管理员及人员适用范围，维护者须覆盖完整适用范围，成员由该管理员负责。其他业务管理员不能直接编辑；平台可以转交维护责任。新管理员只需满足管理范围及资格，不能因为其本人业务权限少于角色已有权限而撤销其他员工的既有角色；后续新增/扩大角色权限仍受其本人上限约束。
专用角色责任管理员约束已随v2统一确认，比Q002最初仅要求覆盖范围更严格。角色名称可重复显示，但同一应用、同类角色、同一责任管理员下的名称不可重复；稳定角色编码全局唯一且不可复用。
平台修改通用角色定义时预览所有受影响成员；这是显式修改角色本身，会影响持有该角色的用户，不按管理员当前权限再次裁剪。业务管理员无权编辑通用角色。撤销某管理员个人持有的角色必须修改其用户—角色关系，不能误用停用角色或修改共享角色权限来代替。责任管理员及业务用户之间不开放递归委派。

== D02：组织、员工与生命周期

组织为单根行政树：HEADQUARTERS、BRANCH、DEPARTMENT。总公司为唯一根；根下可有分公司或直属部门，分公司下可有部门，部门下可有部门；最多8层，不允许环、跨根或把分公司挂到部门下。类型与深度不等同。组织名在同父节点内唯一，编码稳定且不复用。
范围选择支持多个组织节点，各节点显式选择仅本节点或含下级，并提供独立全公司选项；全公司是明确标志，不是空数组或通配符。服务端展开节点集合并校验，不靠前端隐藏人员。
员工具有一个主要组织，暂不做兼职/多组织归属；岗位、部门经理仅为资料，不自动授予角色或审批资格。负责人引用稳定员工ID，可以为空；重名待映射不阻断其他已校验资料，不能取第一个同名人员。

[cols="2,6",options="header"]
|===
|事件 |推荐处理
|调岗/岗位调整 |平台在人员变动页预览该人员全部旧业务角色并明确选择新角色；默认撤回其全部旧业务角色，按应用赋予新角色并更新组织/岗位及必要责任关系。只修改此人的成员关系，不修改角色定义、其他人的关系或岗位模板；无新角色时可明确确认空集合。
|管理员调岗/离任 |替换或撤回该管理员本人的业务角色及应撤销的管理委派；其已授出的角色、专用角色定义和其他员工权限保持不变。人员/角色维护责任可转交新管理员或暂由平台接管，不因接管人权限较小裁剪既有授权。
|员工离职/停用 |停用该人员关联账号并增加auth_version，使其旧会话失效；撤销该人员本人的业务成员关系及管理委派/责任。其曾授给别人的关系不撤销，其他人员不受影响；重新入职需要明确启用和重新授权。
|组织停用 |有启用子组织或在职员工时拒绝，先逐项转移/停用；不隐式级联停用整棵树。
|组织移动 |只允许平台操作，预览管理员范围、角色适用范围与成员影响；新路径导致越界的关系撤销，无自动新增授权；涉及批量影响时使用有审计的预览/确认流程。
|组织/员工删除 |第一版不提供物理删除。使用停用、转移及不可复用编码；历史业务记录和审计保留稳定ID。
|===

人员角色替换是单一事务中的“撤旧+授新+资料/责任变更+审计”，新角色校验或版本检查失败则整次回滚，旧角色不先行丢失；禁止先请求撤回、再独立请求赋予而产生半完成状态。人员变动由平台执行，业务管理员的一般授权仍受本人上限约束。
管理员范围缩减与责任转交只更新维护权限，已授出的用户角色不随之撤销；暂时无人负责时由平台处理待接管任务。组织树结构变动属于另一项明确影响多人的管理操作，仍需预览后处理角色适用范围，不能由某个人换岗隐式移动整棵组织。业务记录保存创建时组织ID，不随员工调岗搬迁历史记录。

== D03：账号与认证

员工最多关联一个账号，账号最多关联一个员工；平台引导及明确标记的合成演示账号可无员工，普通业务账号须绑定在职员工。无自助注册、短信登录、第三方登录或跨域SSO。
账号由平台显式创建/导入建号，创建人员资料不自动建号或分配角色。用户名NFKC、trim、转小写后使用[a-z0-9][a-z0-9._-]，3–64字符；唯一、不可修改/复用。真实员工保留经校验的来源用户名，不因测试命名要求批量改名。
demo使用现有6个合成账号及1234；正式建号使用独立随机临时密码，首次登录仅可访问改密/退出，改密成功后再获得业务入口。正常密码至少12字符且不超过72个UTF-8字节，不设通用正式默认值。密码重置由平台执行，强制改密、增加auth_version并撤销旧身份；响应只向操作人显示一次临时值，不写日志或邮件。
本人改密须校验旧密码，成功后所有旧会话失效并重新登录；退出只撤销当前会话。允许多设备登录，不设“后登录踢前登录”；空闲30分钟、绝对2小时沿用现有规则。受保护的最后一个启用平台管理员不得被停用、撤销管理资格或解除最后管理角色。
登录防护使用Redis按账号和IP分别限制：账号15分钟内连续失败5次后暂缓15分钟，IP每分钟最多30次尝试，超限429；成功清除账号失败计数。对不存在/停用/错误密码保持相同401语义，前端不透露账号是否存在。不做永久锁号，设施故障503。

== D04–D06：角色、目录、有效期与数据范围

=== 角色和关系

正式业务角色只归属一个应用；平台管理角色单独归属admin且受保护。历史bootstrap_admin仅为当前跨应用骨架，新增迁移先引入归属并回填受保护的工程引导类型，再逐步迁移演示关系；不能直接将跨应用历史角色强塞某个业务应用，也不改写V1。
RBAC0不开放用户直配权限、不实现角色继承或角色优先拒绝。多个有效角色的权限/数据范围取并集，不持续受历史授予者或当前责任管理员的上限裁剪；一个来源撤销不删除其他来源。角色停用不删除成员，启用前预览恢复影响；物理删除角色、权限、应用第一版不提供。
成员授权和角色权限关系均支持[from,to)，NULL表示无界。UI使用Asia/Shanghai展示并转UTC毫秒存储；“截至某日”转换为次日00:00的排他上界并显示准确时刻。允许在当前授权资格有效时授予未来生效或长期有效关系；其截止时间不必跟随管理员个人角色/委派的截止时间。角色包含的全部权限须为操作者现在有权授予的权限，不能凭“将来可能拥有”预先授予；每条目标关系仍按自身有效期到期。
批量添加成员最多100人/次，预览全量差异，任一越界整次拒绝；移除关系保留审计，重复移除返回幂等成功。覆盖修改携带expectedVersion，版本冲突409，禁止前端静默覆盖或自动重试写入。平台对受保护角色的修改保留独立管理权限检查。

=== 应用与资源权限目录

平台维护应用、资源树和权限点；业务管理员只读目录。应用编码小写且不可变/复用，18系统目录可登记，但只有OA/PMIS实现约定业务。其他系统标记目录阶段，不宣称已接入；未实现权限点不进入可用委派清单。
资源树只描述菜单/功能分组，允许目录和功能节点，最多8层；权限点为应用:资源:动作并关联功能节点，动作使用view/create/update/submit/withdraw/approve/reject/export等显式代码。父目录不隐式授予后代，前端菜单不是权限执行边界。
权限点包含说明、enabled、implementation_status和版本；只有已实现且启用的权限可用于正式授予。新增权限点不会自动加入现有角色或委派；目录导入不能生成接口代码或放开未声明API。
应用停用立即使其业务与委派失效，记录保留，重新启用必须预览恢复影响；权限点停用使所有来源的该点失效，其他点不受影响。第一版不做应用密钥/API网关或外部业务系统远程鉴权SDK。

=== 业务数据范围

为角色权限关系配置SELF、ORG、ORG_SUBTREE、ALL以及必要的组织节点。SELF仅本人业务记录；ORG仅指定节点；ORG_SUBTREE含下级；ALL仅本应用全部业务记录。管理人员范围与业务记录范围是两套字段，不能互相替代。
相同权限点的多角色范围取并集；授予动作与范围模板均不得超过管理员本人业务权限范围及平台委派上限。用户自身SELF按目标用户解释；ORG等节点由服务端检查包含关系。基础导入中“查看/编辑本人”统一将查看和编辑都设为SELF，预览明确展示。
列表在SQL中按认证主体、owner_user_id及记录组织过滤；详情和写操作独立校验，不能只过滤列表。普通用户跨范围访问已有记录返回404；已知功能缺操作权限返回403，避免通过ID探测记录。审批还要求指定审批人及合法状态，不因ALL范围自动成为审批人。

== D07：附件、导入与映射

支持.xlsx，不接受.xls、宏、外链或公式。文件上限20MiB、单表50,000行、100列、解压累计100MiB；采用流式解析及尺寸限制。人员/组织资料仅授权平台人员可查看，业务管理员电话默认脱敏，不提供真实员工批量导出。
拆为组织、员工、账号建号、负责人绑定、权限目录/角色模板五种明确批次；每个批次预览→校验→确认→一次事务提交，前置批次按顺序完成。人员导入不默认建号；权限模板导入不默认给人授予角色。失败整批回滚，不把五个分开的成功批次说成全工作簿原子事务。
来源匹配规则沿用source-audit的本批组织联合匹配。员工编码由系统生成稳定值并保存来源用户名绑定；不按姓名/电话识别同一人。原始用户名与数据库规范化后冲突报错，真实数据不自动合并。
负责人歧义保留未绑定状态及待处理列表；用户可按员工ID选择，不能假定65条单候选就是已核验负责人。缺组织映射、未知动作、全部所需动作目录不完整均阻断对应批次，不猜测权限。空白不授权并警告；无不产生deny；全部仅展开已校验动作白名单。
默认仅新增，存量同编码冲突报错；平台显式选择更新时逐行预览差异并核expectedVersion。更新文件不得默认停用文件中未出现的人。幂等键结合文件hash、映射版本、批次类型和请求键；已成功重试返回原结果。
预览24小时有效；提交重核指纹及依赖版本，变化409，过期410。原上传文件私有存储，完成7天后禁止下载并列为待清理；结果与错误反馈90天后停止在线提供，公共日志无原始单元格。遵守禁止批量删除约束，本机不自动删除文件，只提供明确单文件的人工清理入口；到期禁用访问不冒充已物理删除。错误页分页展示，下载反馈需同等权限，CSV字段防公式注入。原始根目录附件不在此清理范围内。
导入提交产生审计及持久任务状态，前端可轮询结果；任务不使用原始文件名作为磁盘路径。保留聚合统计，任何运行报告不得包含真实姓名、电话、密码或完整错误行。

== D08：授予独立性、人员交接与实时生效

=== 上限变化不追溯，人员变动只改本人

平台减少/恢复管理员个人业务权限、修改可委派清单或结束其管理委派，仅影响该管理员以后可以进行的维护和新增授权；其他员工已成立的用户—角色关系不变，没有跟随暂停或跟随恢复逻辑。
管理员离职停用的是其本人账号/会话，不能把“授予者无效”作为其他人的授权失效条件。角色维护责任和人员责任由平台转交或待接管；交接只变更维护归属，不能按新管理员较小的业务权限裁剪旧授权。
人员调岗用目标人员的完整新角色集合覆盖旧角色集合，组织/岗位及必要管理委派变化一起校验、提交并审计；离职是本人旧业务角色撤回且账号停用。二者均不修改其他员工关系，也不修改共享角色定义。
独立生效不等于永久有效：目标员工自己的账号停用、角色/权限/应用被明确停用、成员/角色权限关系到期或被明确撤回时仍正常失效；这是对目标授权事实的变化，不是管理员个人变动造成的级联失效。
交接需要双方管理范围及相关元数据版本校验，只能平台执行；若新管理员范围不足，相关维护责任留给平台，其他员工可继续使用既有角色。对于超出新管理员个人业务权限的既有角色，其可在合法范围撤回，但不能重新授予或新增其不拥有的权限。

=== 一致性与请求边界

第一版完整RBAC0继续逐请求读取MySQL当前授权，Redis只承载Session、登录限流和必要任务协调；不提前加入权限快照缓存。业务权限读取目标用户自己的账号、应用、角色、关系和组织事实，不加入授予者当前状态；管理写入另读操作者当前权限/委派/责任范围并进行一致性校验。每次权限检查固定同一Clock时刻。
授权写入、审计和outbox事件同一MySQL事务；敏感授权写在提交前重新检查操作者范围、本人权限和目标版本，并对相关授权主体采用稳定ID顺序加锁，防止交叉修改死锁/越权。授权事实不依赖异步Redis消息生效。
保存接口在事实源提交后返回APPLIED；异步通知/投影另记PENDING，不将投影滞后说成授权未生效。后续确因性能需要增加缓存，必须单独实现design中的版本/nextChangeAt/outbox校验并回归，不能用TTL替代撤权一致性。
撤权提交后新发起请求必须用新事实；已在执行的普通读请求不追溯回收响应。授权、审批等敏感写在提交前复核并与相关授权变更串行化；失败回滚。计划生效/到期无需定时清理触发才生效。
必要数据库/Redis不可可靠读取时503；授权不足403。任务临时故障按1/5/30/60/300秒退避重试，10次后待人工重试，保留幂等键；消息投递不是跨MySQL/Redis原子事务，不发布因管理员个人失权而撤销下属授权的事件。

== D09：OA公文最小完整闭环

对象字段：id、稳定公文编号、标题（1–160字）、正文纯文本（最多10,000字）、owner_user_id、创建组织、当前审批人、状态、version及创建/更新时间。状态为DRAFT、SUBMITTED、APPROVED、REJECTED、VOIDED；审批历史独立追加，只读。第一版无富文本、附件、会签、抄送或多级审批。
公文编号由服务端生成并有唯一索引，不能用时间戳单独保证唯一。创建者为当前认证账号，不能通过请求给他人代建。修改、提交、撤回、作废都需要相应权限点及记录范围；草稿编辑限本人，审批人不能改正文。

[cols="2,3,3",options="header"]
|===
|动作 |状态变化 |补充条件
|创建/编辑 |创建DRAFT；DRAFT或REJECTED内编辑 |本人，具create/update权限；变更version
|提交 |DRAFT或REJECTED→SUBMITTED |本人；具submit；必须选择当前可审批且对该记录有范围的其他账号
|撤回 |SUBMITTED→DRAFT |本人且具withdraw；尚未被审批，撤回与审批并发只允许一个成功
|通过 |SUBMITTED→APPROVED |指定审批人，当前具approve和范围；不得自审
|驳回 |SUBMITTED→REJECTED |指定审批人，具reject和范围；意见必填1–500字
|作废 |DRAFT或REJECTED→VOIDED |本人且具void；不物理删除，无恢复
|===

提交时冻结正文，驳回后可编辑再提交，保留历次审批记录。通过和作废均终态，不编辑/撤回；需要新稿重新创建。审批人失去权限/离职时不能审批，发起人可撤回重选；不自动改派，不开启“超级管理员代批”。
角色模板：OA普通员工（本人查看/创建/编辑/提交/撤回/作废），OA审批员（另有被指派记录的审批动作），OA查看员（经配置范围只读）。普通员工默认SELF；审批员查看/审批默认指定组织的ORG_SUBTREE，实际组织节点由平台/委派上限约束，查看员默认SELF并可在上限内配置其他范围。这些只是可配置模板，不因岗位自动赋予，且须满足管理员自身上限。原权限表中的其他功能点作为目录待实现，不塞入公文闭环。

== D10：PMIS工程项目最小完整闭环

字段：id、稳定项目编号、项目名称（1–160字）、说明（最多2,000字）、计划起止日期、预算DECIMAL(16,2)、owner_user_id、创建组织、审批人、状态、version及时间。预算非负、结束日期不早于开始；第一版只做立项，不含合同、付款、进度、多人项目成员、附件或结项。
创建者是项目负责人，第一版不做负责人转交或代建。状态为DRAFT、SUBMITTED、APPROVED、REJECTED、CANCELLED。草稿/驳回可由本人编辑；提交、撤回、通过、驳回规则与OA同样检查当前权限、范围、指定审批人、自审和并发；本人可将草稿/驳回取消为CANCELLED。经办人默认SELF，审批员查看/审批默认指定组织ORG_SUBTREE，查看员默认SELF；扩大范围均受委派与本人权限上限约束。
已立项APPROVED为此最小闭环终态，不能用编辑接口改预算或负责人；后续变更立项必须作为新需求。角色模板为PMIS项目经办人、立项审批员、查看员，不因“项目经理”岗位自动授权。OA和PMIS各自表/状态机/权限点，不共用万能业务表。

== D12：工程、验收与交付

=== 模块与数据模型增量

保留Java21/Boot3、单一Maven模块化单体、Vue3/TS三应用、MyBatis/MySQL、Redis Session。新增administration功能包承接跨身份/授权的管理用例，通过公开服务组合identity、authorization、audit/imports；权限核心不依赖security/HTTP/OA/PMIS，identity不反向依赖authorization。导入使用公开写命令，不直连其他模块内部Mapper。

=== 已确认的项目性能与测试验收目标（尚未实测）

课程第一版将“万级”解释为10,000个在线会话，并以每会话平均10秒一次请求形成约1,000请求/秒的持续负载；不等价于10,000QPS或10,000同时在途。30ms用于热路径授权计算的服务端p95，含授权SQL与范围判断，不包括登录BCrypt、前端渲染和网络往返。这是用户已确认的项目验收目标，教师要求若不同需显式调整；不能宣称已获教师同意或已经达标。
参考验收环境为应用/依赖合计至少8vCPU、16GiB内存、SSD，本机单实例起步，压测机独立；记录实际CPU/RAM、数据库/Redis版本、连接池、网络RTT和资源使用。若环境不足，记录真实环境结果及差异，不伪称等价参考环境。
合成数据至少10,000人员、111组织、18应用目录、500业务角色、2,000权限动作、每人平均3角色；OA/PMIS各100,000条记录，含有效期、范围、责任管理员和低权限样本。不把这些合成数量冒充附件原始权限动作数。
预热2分钟、稳态15分钟、目标1,000请求/秒，混合比例80%受保护业务读、15%管理只读、4%管理/业务写、1%登录；另做导入与冷启动测试。实际用户思考时间和负载模型随脚本记录，不同时声称为固定并发/固定到达率两种模型。
