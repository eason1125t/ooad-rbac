== 真实表头与质量事实

=== 组织

真实列是 `部门名称`、`部门经理`、`上级部门`，不能把此前线索里的“负责人姓名”当作真实表头。

* 111 个组织名称均非空、唯一；1 行上级部门为空，对应唯一根节点。
* 非空上级部门均能精确关联现有组织；无悬空父节点，无环。
* 根为深度 0，深度 0/1/2 的节点数分别为 1/20/90。深度不能直接等同组织类型；直属部门与分公司可能处于同一深度。
* 员工表“分公司”列有 10 个不同组织标签，均能关联部门表，且其中包含总公司标签。因此不能直接报告为“10 家分公司”。
* 111 行部门经理均非空，共 110 个姓名标签。在全体员工中，65 行经理姓名只有一个候选，46 行有多个同名候选，没有完全找不到的姓名。唯一姓名候选也仅是匹配建议，正式负责人绑定仍采用确认的账号/员工 ID。

=== 员工

真实列是 `姓名`、`用户名`、`分公司`、`部门`、`岗位`、`电话号码`。

* 10,000 行的六列都无空值；用户名与电话号码均为 10,000 个不同值，无重复。
* 姓名仅有 7,859 个不同值，存在 1,596 个重名组，重复超额行数为 2,141。不能用姓名作为人员唯一键。
* 当前电话号码均匹配 11 位数字；这只说明格式，不证明号码真实、本人持有或可作为认证凭证。电话号码不作为账号主键。
* 有 54 种岗位标签、24 种部门标签。岗位不等于角色，导入员工不自动授予五种角色之一。
* 本批文件 NFKC/边缘空白清理前后未出现值变化；将来新批次仍需执行显式标准化校验。

组织匹配必须联合“分公司”和“部门”，本次只读预览按下述顺序匹配：

. 若部门值等于分公司值且存在对应组织，则直接关联该分公司/总公司节点：54 行。
. 若部门名称精确存在，并且该部门的真实父节点等于该分公司，则关联该子节点：190 行。
. 否则仅在该分公司的真实子节点集合中寻找 `分公司 + '-' + 部门`（兼容无分隔符但不得额外造节点），且必须唯一：9,756 行。
. 无结果/多个候选均报错，本次分别为 0/0；三类成功行合计 10,000。

上述前缀规则针对本批实际命名核实。不能无条件向部门名称拼接分公司前缀，也不能仅凭同名部门在全表中选第一条。显示名称和稳定组织编码分开维护；正式导入预览保留原始值与解析后的组织 ID，方便核对。

=== 标准化、动作与范围

* 标识先 NFKC + trim，再按项目统一规则形成比较键；账号若采用小写，应在数据库唯一索引和 API 一致实施。原始显示值不得被账号规范化误伤。本批无标准化碰撞，后续仍须检测。
* 权限按显式词典拆分 `/`；`查看/view -> view`，`新增 -> create`，`编辑 -> update`，`审批 -> approve`，`导出 -> export`。`view` 与本轮迁移的 `oa:document:view`、`pmis:project:view` 保持一致；未知词为校验错误，不能静默丢弃或当作全量。
* `无`、空白均不产生授权；空白额外列入预览警告。`无`不等于优先拒绝条目，RBAC0 中其他有效角色仍可授予同一操作。
* `全部`只展开到该应用/资源经过校验的动作白名单。白名单来自功能动作目录及实现契约，不能使用 `*`，不能给未定义的删除/审批等操作放权。缺少完整动作定义的功能标记 `ACTION_CATALOG_REQUIRED`，只阻断该目录提交分支。
* `查看本人 -> view + SELF`。`查看/编辑本人`中的“本人”作用域歧义需预览显示；安全建议将该格所有授予动作限定 SELF，确认后入库，禁止擅自放宽 view 为全量。本轮不导入这六格。范围信息当前未建列，正式导入前须新增明确模型。
* 动作与范围分开表示。OA 创建者和 PMIS 负责人等业务归属，后端从认证主体与业务记录获取，不能信任客户端 userId。列表在 SQL 查询时过滤；完整业务实现属于下一轮。
* 来源不提供授权生效/到期时间、账号密码、账号状态、应用编码和权限编码。不能伪称从附件读出这些数据。校验预览提供必填配置/确认项；正式管理员密码来自环境变量，真实员工账号不自动获得通用默认密码。

== 后续导入生命周期与错误规则

. 读取并校验文件签名、工作表、表头和尺寸；拒绝缺列/新增未知列与公式值，保留批次指纹。源文件只读。
. 预览阶段构建组织依赖图，校验唯一根、父节点、环、用户名重复和组织映射，再解析角色模板、动作与范围。预览不创建/修改正式账号。
. 负责人绑定在员工 ID 可用之后执行。46 行同名负责人需要确认账号；其余 65 行为可核实候选。负责人资料未解决可单独暂缓，组织和员工无关字段校验继续。
. 同批重复账号为错误；同批完全相同目录项不静默吞掉，给出重复行定位。与存量同编码冲突默认拒绝，显式选择更新时携带 expectedVersion 并审核字段差异。曾使用编码默认不复用。
. 组织、员工/账号、负责人、角色权限目录按依赖顺序提交；每个明确提交批次在一个数据库事务内全部成功或回滚。大文件若未来必须分片，先定义分片原子边界，不将部分成功报告为批次成功。
. 用 `(source_hash, mapping_version, import_kind, idempotency_key)` 识别重试；相同已成功请求返回已有结果。修正映射或内容生成新预览版本，提交必须引用已校验的预览与指纹；不重跑旧失败状态覆盖新状态。
. 错误行反馈包含批次、工作表、行列、错误码、脱敏问题描述、建议动作。账号/电话仅在授权预览界面按最小必要展示；公共日志只记 traceId、批次及聚合计数，不记录真实单元格值。
. 角色/权限更新与审计/同步事件在同一 MySQL 事务内；提交后同步 Redis，响应区分“已保存/同步中/已生效”。本轮只设计，不宣称完整导入或可靠同步平台已经实现。

建议错误码：`HEADER_MISMATCH`、`REQUIRED_EMPTY`、`DUPLICATE_KEY`、`NORMALIZATION_COLLISION`、`PARENT_NOT_FOUND`、`ORGANIZATION_CYCLE`、`ORGANIZATION_AMBIGUOUS`、`MANAGER_AMBIGUOUS`、`UNKNOWN_ACTION`、`ACTION_CATALOG_REQUIRED`、`SCOPE_CONFIRMATION_REQUIRED`、`VERSION_CONFLICT`。
